LocalFind

One place to discover small businesses in your neighborhood.

Information story

Who it helps and why

The story

Community members want to find small businesses around them — cafes, salons, boutiques, repair shops — without jumping between apps.

Who benefits

  • Residents — discover shops they did not know existed nearby
  • Small-business owners — more discoverability when listings are easier to find in one feed

Why it matters

  • Many local shops are invisible next to big chains on general search
  • Supporting nearby businesses keeps money in the community
  • One simple search beats checking Yelp, Google, and social separately

The problem today

People cannot see what is already around them

  • Most people do not know how many small businesses exist near home or work
  • There is no single way to answer “what local shops are near me?”
  • Information is split across many sources — Yelp, Google Maps, Instagram, chamber websites, owner pages
  • Each source uses different fields, rankings (often ads), and rules — so every search feels like starting over

The data exists. It is just not combined in a form people can actually use.

Existing information

FAIR assessment — our two live sources

FAIR principle Yelp Fusion API OpenStreetMap
Findable Partial — IDs exist, no stable civic URI Partial — node/way IDs, geo search
Accessible Partial — API key, rate limits, terms Partial — free but throttled; attribution required
Interoperable Low — Yelp-specific schema and categories Partial — tag-based; uneven hours/contact
Reusable Low — display-only; no provenance in payload High — ODbL 1.0 with attribution

Yelp brings ratings, photos, and hours. OSM brings open map data and coordinates. Neither alone fits our community discovery story.

Our solution

SBP v1.0 — one portable structure + LocalFind app

Yelp+OSM →normalizer →cache →API →LocalFind UI

Design decisions (FAIR gaps)

  • Findable — stable id, schema_version
  • Accessible — REST API + web search (ZIP, category, near me)
  • Interoperable — one JSON shape; Yelp + OSM mapped the same way
  • Reusable — provenance + quality_flags on every response
{
  "schema_version": "1.0",
  "provenance": {
    "source": "Live merged feed",
    "license": "ODbL; Yelp display terms"
  },
  "businesses": [{
    "id": "yelp-abc123",
    "name": "Glasswing",
    "categories": ["fashion", "retail"],
    "rating": 4.8,
    "location": {
      "address_line_1": "806 E Roy St",
      "city": "Seattle",
      "zip_code": "98102"
    },
    "hours": { "monday": "11:00-18:00" },
    "yelp_url": "...",
    "osm_url": "...",
    "quality_flags": { "has_address": true }
  }]
}

We merge both APIs into one record so the app shows name, location, hours, and links in one place.

Quality control

Quality, performance, and security tradeoffs

Quality

JSON Schema contract; completeness_score per batch

12 automated tests (schema, auth, live mocks)

Gap: OSM rows may lack ratings — Yelp enriches on detail

Performance

Cached search ~20–100 ms (fast=true)

Live refresh ~15–40 s (Yelp + OSM)

Tradeoff: cache speed vs freshest listings

Security

Public responses hide owner phone/email

Bearer token unlocks restricted contact

API keys only in .env, never in responses
